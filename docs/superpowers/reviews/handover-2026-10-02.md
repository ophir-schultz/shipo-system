### FIRST-HAND, 2026-10-03: 896 duplicate shipment rows in production

Added after the merge to `main`. This is the one item in this document that is a
statement about the **live database**, not about the tree. Ophir ran every query
below in the Supabase SQL editor and reported the results; I did not touch the
database.

A pre-flight for `ledger_03_charges.sql`'s unique index found **one
`shipmentId`, `340970367`, on 896 of 1,659 `shipments` rows — 54% of the
table.** The arithmetic says it is one event and not generalised drift:
1,659 − 896 = 763 rows left against 764 − 1 = 763 remaining distinct ids, so
every other id holds exactly one row.

They were genuine duplicates, not distinct shipments sharing a junk id. Across
the 896 rows, `count(distinct …)` of `raw_data`, `order_number`,
`tracking_number`, `carrier`, `raw_data->>'orderNumber'` and
`raw_data->>'trackingNumber'` was **1 for all six**, and every row was stamped
`2026-09-25 00:00:00+00`.

- `sum(actual_cost)` = **$6,890.24** over 896 rows = **$7.69 each**. One real
  shipment, so **$6,882.55 of phantom carrier cost** was inflating cost and
  deflating profit in anything that sums `actual_cost`.
- `sum(client_rate)` = **NULL, not 0** — never priced, never invoiced.
  **This is §"The through-line" earning its keep against real data.** Under the
  pre-branch behaviour these rows would have carried `client_rate: 0`, the sum
  would have read `0`, and 896 phantom rows would have been indistinguishable
  from 896 genuinely free shipments. The doctrine caught a production error
  before the code that enforces it was deployed.

**Cause — identified first-hand in the deployed code, not guessed.**
`origin/main:src/lib/sync/shipstation.ts:28-32` is the dedup check:

```ts
const { data: existingShipment } = await supabaseAdmin
  .from('shipments')
  .select('id, actual_cost, client_id')
  .eq('order_number', String(s.orderNumber))
  .single()
```

`.single()` raises an error whenever the match count is not exactly 1 — and that
**includes two or more**. The error is destructured away, so `data` is `null`,
`if (existingShipment)` is false, and control falls through to
`insert(shipmentData)` at `:114`. The guard against duplicates becomes a
generator of them.

It is self-amplifying, which is what turns a bug into 896 rows. At 0 matching
rows it inserts; at 1 it updates correctly; but **once the table holds 2 rows for
an order number, `.single()` fails on every subsequent poll and every poll
inserts another row.** Crossing from 1 to 2 — a race, a retry, anything — is
irreversible under this code. With three unattended crons a day, nothing stops
it.

This is the branch's own through-line in production: **a failed read collapsing
into "not there".** `PGRST116` means *I could not reduce this to one row*, and
the code read it as *there is no such row*.

Two independent things fix it, and the branch has both:

- **The code.** `src/lib/sync/shipstation.ts:86-97` (comment: `DEFECT 4,
  FIXED`) uses `.maybeSingle()`, binds `error: matchError`, inspects it, and
  `continue`s via `run.fail(...)` instead of falling through to an insert. It
  also keys on `shipstation_shipment_id` rather than `order_number`, so a
  multi-package order no longer collides by construction.
- **The constraint.** `shipments_shipstation_id_key`
  (`ledger_03_charges.sql:24`) makes the re-insert impossible at the database
  level even if the code is wrong again.

But the damage blocked the index that prevents recurrence, which **forces the
order: reconcile → migrate → deploy.**

**The live exposure, stated precisely.** Reconciliation deduplicated on
`shipmentId`. The *deployed* code keys on `order_number`. Those are different
keys, so reconciliation does **not** prove the loop is disarmed — any
`order_number` currently holding ≥ 2 rows re-arms it at the next cron. That
check is one query and it has not been run:

```sql
select order_number, count(*)
from shipments
group by order_number
having count(*) > 1
order by 2 desc;
```

Zero rows means the loop cannot fire before the deploy. Any rows means it can,
and the crons should be paused until the migrations land.

**Reconciled, verified clean.** Ophir deleted the 895 duplicates in a
transaction keeping one row (`remaining 1 / cost 7.69`); `count(*)` then read
**764**, cross-checking exactly against the independently measured 764 distinct
ids. `shipments` has one inbound FK, `rate_adjustments_shipment_id_fkey`, whose
`delete_rule` is **`NO ACTION`** — Postgres would have *aborted* the delete had
anything referenced those rows. It committed, therefore nothing did.
`rate_adjustments` reads 11 rows, 0 null `shipment_id`, 0 orphaned.

**The reasoning shape is worth reusing.** My first check asked for integrity
counts, and `11 / 0 / 0` proves nothing on its own: a CASCADE deletes both sides
and leaves referential integrity intact behind it. Consistency cannot
distinguish "nothing was referencing these" from "everything referencing these
was deleted too." It was the **delete rule** that settled it — by construction,
not by inference.

Two things that must not be done to this:

- **Do not "fix" a unique violation by dropping the index.**
  `ledger_03_charges.sql:20-23` says to stop and reconcile instead.
- Note that the backfill at `ledger_03_charges.sql:14-18` would stamp
  `340970367` onto all 896 rows *before* the index creation failed. That is
  harmless only because the file is pasted as one statement batch and rolls

### The through-line

Every one of them is one defect: **0 used as a stand-in for "I could not find
out".**
The doctrine the branch now enforces structurally:

- **null = UNKNOWN, 0 = a decision somebody made.** Enforced in *both*
  directions — a stored 0 still renders `$0.00`, not a dash. Dashing a real 0
  would raise a question about a decision that was actually made.
- **"Could not read" is not "is not there."** A failed read skips or refuses;
  it never writes a zero.
- **A wrong-but-plausible number is worse than UNKNOWN**, because nothing
  downstream can question it and no alert can be written for it.
- **Changing a sentinel can silently disarm an existing alarm.**
  `.eq('client_rate', 0)` never matches NULL. That was the decisive catch in
  `a4366d4` — writing NULL without touching `monitor/route.ts` would have
  switched off the only existing alarm for the exact condition being fixed.

### `src/lib/billing/unpriced.ts` — the shared module

One module rather than ~15 inlined copies, because two copies of a money rule
drift and the drift is in money. A `.ts` and not a hook because
`vitest.config.ts` **excludes `.test.tsx`**, so nothing in a component file can
be tested in this repo at all.

The API is deliberately hard to misuse:

- `sumPriced(rows, key)` returns `{ total, unpriced, counted }`, not a number.
  A caller cannot render the total without the withheld count in hand, so
  rendering an incomplete total silently is now a deliberate choice rather than
  the default.
- `combinePriced(...parts)` exists because `a.total + b.total` is exactly where
  the counts get dropped.
- `unpricedNote(n, noun)` returns `''` when nothing was withheld. Not
  "all priced" — a permanent all-clear next to every total is how a real
  warning stops being read.
- `UNPRICED_CELL = 'UNPRICED'` is text, not a number, so `SUM()` over a
  spreadsheet column skips it. That is the honest arithmetic.
- Totals accumulate in **integer cents**.

19/19 mutations caught across `unpriced.ts`.

### A.3 `weightToLb` floored an unknown weight to the cheapest row — CLOSED by `8ed5bf6`

**Not in the original review at all.** Surfaced while fixing A.2.
`Math.ceil((weightOz || 0) / 16)` with `if (lb < 1) return 1` sent an absent,
zero or NaN weight to **matrix row 1, the cheapest row.** `|| 0` and the `< 1`
floor were each individually defensible; together they turned missing data into
the lowest invoice line the card allows.

Two things worth carrying forward:

- **The legacy card had the same hole, which fixing only `weightToLb` would have
  hidden.** `matchLegacyRate` already refused a non-finite weight but *accepted
  0*, so an unweighed shipment matched any band open at the bottom and was billed
  the **lightest** band. Both cards are reachable for one shipment, so the
  judgement now lives in one function, `billedWeightOf`, which both ask.
- **`error` vs *miss* is a decision about caller behaviour.** An `error` makes
  `recalculate` skip the row and keep the previous price — right for a dropped
  connection, wrong for a missing weight, which will still be missing next run
  and would hold a stale price forever with nothing on screen. So an unusable
  weight is returned as a **miss**, which falls through to `matchLegacyRate`,
  whose weight guard fires *before* its no-card branch, so the row is written
  UNPRICED naming the weight. `recalculate.ts` needed no control-flow change.

### A.5 Seven diagnostics scanned unpriced as `client_rate = 0` — CLOSED by `dfb4b0a`

Filed here as open item 2, before the open list below was renumbered to close
this. **The count was right this time — seven.** What the
filed entry got wrong was the last sentence it ended on: *"The fix is mechanical;
the only judgement is whether a given script wants NULL-only or both."* Matching
the predicate was the small half. Matching the **reporting** was the rest of it,
and it moved two figures that were overstating their case:

- `diag-simulate-fix`'s `"would price: N"` counted free-card zeros as Section A
  wins. A free-card zero prices at $0 whatever the zone chart says, so it was
  never broken and Section A was never going to fix it.
- `gen-rate-card-worklist` told the operator to create a rate cell for a
  shipment whose card **already says free**. It now says so and shows the
  stored rate instead.

Neither was visible from the predicate alone, which is why "mechanical" was the
wrong word: the filed entry treated a reporting defect as a filter defect.

**The two conditions are selected but deliberately not merged**, mirroring
section 4a of `monitor/route.ts`, which runs them as two counts with two
messages. NULL means the card does not cover the shipment; 0 means *either* a
row last priced before unknown became NULL *or* a card that genuinely says free,
and nothing in the column tells those apart. A merged total would assert every
legacy zero is an uncovered shipment — the same species of confident wrong
number these scripts exist to find. The predicate now lives once in
`scripts/unpriced-filter.mjs` instead of seven times.

Three traps worth keeping:

- **`numeric(10,2)` arrives over PostgREST as the quoted string `'0.00'`**, so
  `=== 0` would have filed a stored zero under NO RATE and double-counted it as
  uncovered. Classification imports the real `priceOf` from
  `src/lib/billing/unpriced.ts` — pure and import-free, so Node's type stripping
  loads it with no `@/*` alias to resolve (A.2) — rather than restating `== null`.
- **`rateKind` takes the ROW, not the value, and throws if `client_rate` is
  absent.** None of these scripts selected the column. A never-read column
  answers `undefined`, which `priceOf` correctly calls UNKNOWN, so without that
  guard every legacy zero in the table would have been filed under NO RATE and
  reported as a confident, wrong split.
- **Chained `.is()` and `.eq()` on one builder is an AND and matches nothing**,
  so the union is a single `.or()`. `diag-zonelookup` instead samples each kind
  separately, because PostgREST promises no ordering and its `limit` over the
  union could have come back all of one kind while saying nothing about the other.

Pinned by `src/lib/billing/unpriced-filter-parity.test.ts`, which **scrapes the
route's two query builders as text** — an `.or()` string and two PostgREST
builders inside a route handler cannot be made the same object — strips
whole-line comments first, and asserts **set equality, not a superset**: if the
monitor grows or drops a condition, the scripts are describing a different
population than the live alarm. Like A.4 it asserts both agreement and the
expected answer.

**Three further defects were found in these same scripts and fixed on top:**

- **`b3d1728` — the worklist was written from an uncapped `.select()`.**
  PostgREST caps a `.select()` with no `.range()`, so a capped read did not
  merely undercount: it dropped whole clients off the list of people whose card
  needs cells, and **an absent client reads as a client whose card is
  complete.** The exact count is now requested and compared, and the warning
  goes in the **document** rather than only the console — the file is what gets
  read, often long after the run, by someone who never saw the terminal.
- **`3491c3c` — none of the worklist's reads checked `error`.**
  `splitUnpriced(null)` answers an empty population quite happily, so a failed
  shipments read produced "Generated from the 0 shipments" and a worklist with
  no clients in it, which reads as *there is no rate-card work to do*. The most
  alarming possible result rendered as the most reassuring one. Both reads now
  refuse **before** `writeFileSync`, so an existing worklist is left intact
  rather than overwritten with an empty one — stale is a true record of a run
  that worked, which empty is not.
- **`7a1e8b9` — the other six printed `0`, `none at all`, `NOT IN CHART`,
  `no rate cell` for reads that never happened.** Those are not neutral blanks;
  they are the most alarming answer each question has, produced by the script
  rather than by the data and indistinguishable from a clean result. The policy
  now lives in `scripts/read-or-refuse.mjs`, and it is decided **per read, not
  per script**: *refuse* for a read the whole report is computed from, *UNKNOWN*
  for a per-item read, because one client's unreadable card must not discard the
  other clients' rows — but must not render as an empty card either, since an
  empty card and an unread card send an operator in opposite directions.

That last one is the fourth time this branch has collapsed a duplicated rule
into one module — after `unpriced.ts`, `zone-weight.mjs` and
`unpriced-filter.mjs`. `gen-rate-card-worklist`'s own local `refuse()` from
`3491c3c` was deleted in favour of the shared one, so there is one definition
