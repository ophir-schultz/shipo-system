### The through-line

All three are one defect: **0 used as a stand-in for "I could not find out".**
The doctrine the branch now enforces structurally:

- **null = UNKNOWN, 0 = a decision somebody made.** Enforced in *both*
  directions — a stored 0 still renders `$0.00`, not a dash. Dashing a real 0
  would raise a question about a decision that was actually made.
- **"Could not read" is not "is not there."** A failed read skips or refuses;
  it never writes a zero.
- **A wrong-but-plausible number is worse than UNKNOWN**, because nothing
  downstream can question it and no alert can be written for it.
- **Changing a sentinel can silently disarm an existing alarm.**
  `.eq('client_rate', 0)` never matches NULL. That was the decisive catch in
  `a4366d4` — writing NULL without touching `monitor/route.ts` would have
  switched off the only existing alarm for the exact condition being fixed.

### `src/lib/billing/unpriced.ts` — the shared module

One module rather than ~15 inlined copies, because two copies of a money rule
drift and the drift is in money. A `.ts` and not a hook because
`vitest.config.ts` **excludes `.test.tsx`**, so nothing in a component file can
be tested in this repo at all.

The API is deliberately hard to misuse:

- `sumPriced(rows, key)` returns `{ total, unpriced, counted }`, not a number.
  A caller cannot render the total without the withheld count in hand, so
  rendering an incomplete total silently is now a deliberate choice rather than
  the default.
- `combinePriced(...parts)` exists because `a.total + b.total` is exactly where
  the counts get dropped.
- `unpricedNote(n, noun)` returns `''` when nothing was withheld. Not
  "all priced" — a permanent all-clear next to every total is how a real
  warning stops being read.
- `UNPRICED_CELL = 'UNPRICED'` is text, not a number, so `SUM()` over a
  spreadsheet column skips it. That is the honest arithmetic.
- Totals accumulate in **integer cents**.

19/19 mutations caught across `unpriced.ts`.

### A.3 `weightToLb` floored an unknown weight to the cheapest row — CLOSED by `8ed5bf6`

**Not in the original review at all.** Surfaced while fixing A.2.
`Math.ceil((weightOz || 0) / 16)` with `if (lb < 1) return 1` sent an absent,
zero or NaN weight to **matrix row 1, the cheapest row.** `|| 0` and the `< 1`
floor were each individually defensible; together they turned missing data into
the lowest invoice line the card allows.

Two things worth carrying forward:

- **The legacy card had the same hole, which fixing only `weightToLb` would have
  hidden.** `matchLegacyRate` already refused a non-finite weight but *accepted
  0*, so an unweighed shipment matched any band open at the bottom and was billed
  the **lightest** band. Both cards are reachable for one shipment, so the
  judgement now lives in one function, `billedWeightOf`, which both ask.
- **`error` vs *miss* is a decision about caller behaviour.** An `error` makes
  `recalculate` skip the row and keep the previous price — right for a dropped
  connection, wrong for a missing weight, which will still be missing next run
  and would hold a stale price forever with nothing on screen. So an unusable
  weight is returned as a **miss**, which falls through to `matchLegacyRate`,
  whose weight guard fires *before* its no-card branch, so the row is written
  UNPRICED naming the weight. `recalculate.ts` needed no control-flow change.

**The import question the filed entry asked has a definite answer: `zones.ts`

  survivor this session: "accumulate dollars as floats instead of cents"
  survived because the test used `[0.1, 0.1, 0.1]`, which sums to exactly `0.3`

  `3.3000000000000007` vs `3.3`.

  `true`: every comparison against NaN is false, so both range guards passed and
  the function fell through to `return true` — meaning *every* band claimed to
  cover an unreadable weight. The test was right and the module was wrong.
- **A surviving mutant can mean the CODE is wrong, not the test.** In `8ed5bf6`
  a mutant deleting `billedWeightOf`'s opening
  `=== null || === undefined || === ''` guard survived — because all three terms
  were unobservable. `typeof null` is `'object'` so the type guard below already
  caught null and undefined, and `Number('')` is `0`, refused two lines down.
  The guard had been copied from `shipmentProfit`, where the identical line **is**
  load-bearing because there 0 is a legitimate value. Deleted rather than
  test-covered: a line that reads as the thing doing the work, and is not, is
  worse than no line.

  run: deleting the `typeof` guard also survived, until the cases that
  distinguish it were added. `Number(true)` is `1` and `Number([5])` is `5`, so

  prove nothing about that guard.
